# WEBUI-APPS requirements

| ID | Requirement | Verification |
|---|---|---|
| `APP-01` | **Browser identity consistently reads GraphOS across titles and assets.** Agent-webui's page titles, metadata, web manifest, generated assets, theme tokens, UI copy and published Pages site consistently present the GraphOS product identity. | Asset regeneration, a rendered snapshot test and the Pages build confirm consistent branding. |
| `APP-02` | **Package, import and environment naming stay on the component identity.** Agent-webui's package and import names (`agent-webui`, `agent_webui`), npm metadata, release image, WebMCP identifiers, skills, browser storage and consent keys, and environment variable names are unchanged; only user-visible strings carry the Graph OS brand. Operator decision 2026-10-09: only front-end-facing items are renamed to Graph OS; agent-webui stays the component name. | Build and wheel tests confirm the component identifiers are unchanged while user-visible strings read Graph OS. |
| `APP-03` | **AppSurface contract declares each app's route, capability and client.** Agent-webui exposes Apps as a single section in nav-registry.ts, where each app declares its route, required capability, typed service client, WebMCP page and optional Atlas renderer through one AppSurface contract. | Contract tests and a route-census test confirm every registered app conforms to the AppSurface shape. |
| `APP-04` | **Contributed app descriptors cannot escalate privilege beyond the contract.** Native apps and validated package-contributed apps resolve to the same AppSurface shape, and an untrusted or malformed app descriptor cannot register executable code, an arbitrary URL, or a capability beyond what the contract grants. | Tests that submit invalid descriptors and denied capabilities confirm they are rejected. |
| `APP-05` | **Markets consumes the AppSurface contract without shell-side duplication.** The Markets app consumes the AppSurface contract as its first app, without the browser shell duplicating Markets' scanner, chart or gateway wiring. | A first-consumer integration test confirms Markets runs through the shared contract alone. |
| `APP-06` | **No browser-state migration is required by the rebrand.** Because storage and consent keys keep their component names, existing browser state and granted permissions stay valid. Any future key change must expire or migrate them with explicit renewed consent. Operator decision 2026-10-09: only front-end-facing items are renamed to Graph OS. Agent-webui stays the component name. | Browser test confirms existing consent and storage survive the user-visible rebrand. |
| `APP-07` | **App navigation supports accessibility and layout states across devices.** Navigation between apps in agent-webui works with keyboard, touch and reduced-motion input across mobile and desktop layouts, and each app surface presents explicit loading, unavailable and denied states. | An end-to-end accessibility test suite confirms these interaction modes and states. |
| `WEBUI-APPS-R001` | **Apps information-architecture section and AppSurface contract.** Agent-webui introduces an Apps section in its navigation information architecture and a reusable AppSurface contract that binds each app's route, capability, typed client, WebMCP page and optional Atlas renderer to the existing shell. | Contract and route-census tests confirm the shared shell binds every declared app surface correctly. |
| `WEBUI-APPS-R002` | **Graph OS brand layer covers user-visible strings.** Page titles, metadata and the web manifest name and short name must present the Graph OS brand. The Open Graph card, UI copy and user-facing documentation headings must present the Graph OS brand. Operator decision 2026-10-09: only front-end-facing items are renamed to Graph OS; agent-webui stays the component name. | A rendered snapshot test and asset checks confirm user-visible strings read Graph OS. |
| `WEBUI-APPS-R003` | **Repository, package and runtime identifiers are not renamed.** The repository, distribution, Python import path, npm package, WebMCP identifiers, skills, browser storage keys, consent version, environment variables and release image keep the agent-webui identity. Operator decision 2026-10-09: only front-end-facing items are renamed to Graph OS; agent-webui stays the component name. | Build and packaging tests confirm the identifiers are unchanged. |
| `WEBUI-APPS-R004` | **Run harness surface is read-only and honest.** The agent-webui client must show a run's current plan, context use against budget, applied harness configuration, cost and termination reason. The client reads only graph-os operations. | Children WEBUI-APPS-R004.1 to WEBUI-APPS-R004.6. |
| `WEBUI-APPS-R004.1` | **Run read goes through the graph-os read operations.** The client run view must read `runs.get` and `runs.metrics` (the `GRAPHOS-OPS` rows for run metrics). The client must not call the engine and must not compute these values. | `tests/x::test_run_read_uses_graphos_operations` |
| `WEBUI-APPS-R004.2` | **Applied harness configuration is shown.** The run view must show the run's `harness_config`: `context_policy`, `plan_scaffold` and `action_space`. A missing field must read "not available". | `tests/x::test_harness_config_shown` |
| `WEBUI-APPS-R004.3` | **Context use is shown against the budget.** The run view must show `peakContextTokens` against `contextBudgetTokens` and the cost `costUsd`. An absent field must read "not available", never zero. | `tests/x::test_context_and_cost_shown` |
| `WEBUI-APPS-R004.4` | **Current plan is shown read-only.** The run view must render the current plan from the run's plan state. The view must offer no edit control. | `tests/x::test_plan_read_only` |
| `WEBUI-APPS-R004.5` | **Each termination reason has a distinct state.** The run view must map each `terminationReason` (`final_answer`, `context_overflow`, `stuck`, `step_budget`, `error`) to its own label. `context_overflow` and `stuck` must not appear as a generic failure. | `tests/x::test_termination_reasons_distinct` |
| `WEBUI-APPS-R004.6` | **Absent operation shows an honest state.** When `runs.get` or `runs.metrics` is absent or refused, the run view must show "not available" and no fabricated value. | `tests/x::test_absent_operation_not_available` |
| `WEBUI-APPS-R030` | **Graph view edits go through the engine and refusals show.** The graph view must render nodes and edges as a pan and zoom force layout with semantic filters. It must send add, edit and delete requests to graph-os and show the engine verdict, never a local edit. Persona modes must change only presentation. | Children WEBUI-APPS-R030.1 to WEBUI-APPS-R030.7. |
| `WEBUI-APPS-R030.1` | **Model.** `src/lib/graph-edit.ts` (new) must define `GraphEditRequest` (`add`, `update`, `delete`; node id; labels; properties), `GraphEditVerdict` (`applied`, `refused`, `unavailable`) and `ViewPersona` (`operator`, `analyst`, `reader`). No store type exists for these today. | `src/__tests__/graph-edit-types.test.ts::test_edit_types_closed` |
| `WEBUI-APPS-R030.2` | **Behavior.** `src/lib/graph-edit.ts` must expose `sendGraphEdit` as a named default. It posts one request to the graph-os node operations through `gatewayPost` (`src/lib/gateway.ts:129`) and returns a `GraphEditVerdict`. The graph owner is `EG-TYPED-PACKS-R088`; the operation owner is `GRAPHOS-OPS`. | `src/__tests__/graph-edit-send.test.ts::test_send_returns_engine_verdict` |
| `WEBUI-APPS-R030.3` | **Wiring.** `GraphView.tsx:792`, `:796` and `:801` define `handleUpdateNode`, `handleDeleteNode` and `handleAddNode`, which only change React state and call no server. The caller is `GraphCanvas.tsx:605-609` through `onUpdateNode`, `onDeleteNode` and `onAddNode`. No production caller reaches an engine write today. This row replaces the three bodies with `sendGraphEdit` and changes local state only after an `applied` verdict. | `src/__tests__/graph-edit-wiring.test.tsx::test_handlers_call_send_graph_edit` |
| `WEBUI-APPS-R030.4` | **Refusal.** When the engine refuses an edit for lack of permission, `GraphView.tsx` must keep the node unchanged and show the refusal reason. When the operation is absent, it must show `not available`. The identity owner is `GRAPHOS-IDENTITY`; the client must not decide authorization. | `src/__tests__/graph-edit-refusal.test.tsx::test_unauthorized_edit_refused_and_unchanged` |
| `WEBUI-APPS-R030.5` | **Behavior.** The view must offer semantic filters by node type and by label text through `typeFilter` (`GraphView.tsx:272`). It must offer a persona mode that selects a default filter and detail level. `GraphCanvas.tsx:379` already runs the force layout, with pan and zoom. A persona must not widen what the engine returns. | `src/__tests__/graph-persona-filter.test.tsx::test_persona_changes_presentation_only` |
| `WEBUI-APPS-R030.6` | **Evidence.** Each edit must record the request, the verdict and the engine reason in the view's visible edit log. A refused or unavailable edit must appear there with its reason. | `src/__tests__/graph-edit-log.test.tsx::test_log_records_each_verdict` |
| `WEBUI-APPS-R030.7` | **Hot-path proof.** The user-facing entry point is the graph view `GraphView.tsx` with a selected node. A test clicks save and delete in the overlay (`GraphCanvas.tsx:605`) and passes through `sendGraphEdit`. It observes the refusal reason and the unchanged node for an unauthorized principal. It observes the applied node for an authorized one. | `src/__tests__/graph-edit-hotpath.test.tsx::test_overlay_edit_reaches_engine_and_shows_verdict` |
| `WEBUI-APPS-R031` | **Memory state shows as Markdown files that sync with the graph.** The memory view must list the Markdown files graph-os materializes for observations, reflections, profile and active context. It must show each file's sync state. It must report a conflicting edit as refused with both versions and never overwrite. | Children WEBUI-APPS-R031.1 to WEBUI-APPS-R031.7. |
| `WEBUI-APPS-R031.1` | **Model.** `src/lib/memory-files.ts` (new) must define `MemoryFileKind` (`observations`, `reflections`, `profile`, `active_context`), `MemoryFile` (kind, path, content hash, sync state) and `MemorySyncState` (`in_sync`, `graph_ahead`, `file_ahead`, `conflict`). Search terms used: `MEMORY.md`, `reflections`, `bidirectional`; no match exists. | `src/__tests__/memory-files-types.test.ts::test_memory_file_types_closed` |
| `WEBUI-APPS-R031.2` | **Behavior.** `src/lib/memory-files.ts` must expose `listMemoryFiles` and `saveMemoryFile` as named defaults. Both call graph-os operations through `gatewayPost` (`src/lib/gateway.ts:129`). The engine and the agent runtime hold the files and the sync. The operation owner is `GRAPHOS-OPS`; the graph owner is `EG-DURABLE`. | `src/__tests__/memory-files-ops.test.ts::test_list_and_save_use_graphos_ops` |
| `WEBUI-APPS-R031.3` | **Wiring.** `MemoryView.tsx:439` defines `MemoryView`, which loads Memory nodes from `/api/enhanced/graph/nodes?node_type=Memory` (`:461`) and writes through `/api/enhanced/graph/memory` (`:143`, `:190`, `:492`). It is mounted by the navigation registry and shows no files today. This row adds a Files tab beside `browse` (`:446`) that calls `listMemoryFiles` on load. | `src/__tests__/memory-files-wiring.test.tsx::test_files_tab_calls_list` |
| `WEBUI-APPS-R031.4` | **Refusal.** When `saveMemoryFile` returns a conflict, the view must keep the file unchanged, show the graph version and the file version, and offer no silent overwrite. When the operation is absent, the view must show `not available`. | `src/__tests__/memory-files-conflict.test.tsx::test_conflict_refused_with_both_versions` |
| `WEBUI-APPS-R031.5` | **Behavior.** The Files tab must show each file's `MemorySyncState` with a distinct label per state. A file with a missing state must read `not available`, never `in_sync`. | `src/__tests__/memory-files-state.test.tsx::test_each_sync_state_has_label` |
| `WEBUI-APPS-R031.6` | **Evidence.** Each save must show its content hash, the engine verdict and the time in the Files tab. A conflict must show the hashes of both versions. | `src/__tests__/memory-files-evidence.test.tsx::test_save_shows_hash_and_verdict` |
| `WEBUI-APPS-R031.7` | **Hot-path proof.** The user-facing entry point is `MemoryView` opened from the navigation. A test opens the Files tab, edits one file and passes through `saveMemoryFile`.
